# 未读分类与正常已读回执

用户已授权将当前岗位已读完且已回复的对应消息设为已读。SDK历史采集不触发客户端阅读动作，不能把未读角标全算漏回，或将采集成功称为已标已读。

先以当前岗位UID/姓名与真实发送回执匹配，逐人列出：

- 已回复、无后续新入站，但仍残留未读；
- 已交流，之后有尚未审阅的新消息；
- 尚未发出消息的新招呼或待首次联系；
- 已审但不发消息的确认、条件不全或资料不足。

最后两类不能统称“后续新增”；只有当前新mid和真实采集时间才能证明新增。已问待答不催促，缺失或失败的history不清未读。客户端缓存名单、角标消息条数、未读会话数和远端所见分页分别报告。

## 已验证客户端流程

依据本地实际客户端源码核对后，通过正常应用对象读取 `iBossRoot.messageStore.getChatInfo(uid + '_0_1')`：`newMsgCount`是消息计数，`unreadMidArr`是未读mid。当前源码角标还排除`isFiltered`及`relationType===8`，不能直接拿其他筛选视图的数字比较。

本版本正常阅读事件为：

```javascript
window.top.mediator.publish('SEND_READ', {
  user: {uid, friendSource: 0},
  mid: lastReviewedMid
});
```

这是客户端现有订阅调用transport的`sendRead`，发送阅读回执并同步本地会话状态；不是聊天文字，不调用`sendMessage`，也不通过DOM。不同来源和版本先查实际源码，不照搬`friendSource:0`。

调用前主代理核本人完整快照、成功发送及独立回读的证据；目前未读mid须在已处理范围内。客户端末条mid或未读集合变化时先重新分类，不沿用旧计划。当前实现的本地同步会清空该会话未读集合，因此有未处理新消息时暂不调用，不直接改`newMsgCount`来隐藏角标。

每个会话保存独立阅读回执attempt和结果，正常事件只执行一次，另一次读取会话状态核对。失败或结果未知时保留证据，不能重发聊天文字。只核到本地计数归零时如实说本地读回通过，不能冒称远端持久化已经独立确认。

`messageStore.updateReadMessagesById`用于对方阅读我方消息的状态；不能拿它代替自己的未读回执。`result.readConfirmed`同样描述对方是否已读，不能因自己清未读而改为true。权限拒绝过的`zpchatGetLastRead`不作为替代入口。
